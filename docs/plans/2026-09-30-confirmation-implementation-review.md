# WWM confirmation — implementation and integration review

Status: review only; no application, database, OAuth configuration, event, or email changed. Parent owns product/security decisions and acceptance. Based on `2026-09-30-meeting-confirmation.md` and source inspection on September 30, 2026.

## Current integration map and hard gaps

- `WhenWeMeet.tsx` currently renders Availability / Everyone / People under a single room view, a Share icon and Settings. Add **Confirm** as a fourth, distinct tab rather than replacing any of these. `WeeklyAvailability` is the editable/saved-person calendar, not a safe confirmation selector: isolate a simplified aggregate calendar so selecting cannot invoke `sync.toggle` or save availability. Existing `Room` has `owner_id` and derived `role`, but `role` is a presentation hint only; server must independently verify authenticated `user.id === room.owner_id` on every authorization/mutation.
- `GET /api/craft/when-we-meet/[roomId]/people` calls `wwm_room_people` with membership enforcement; its exact rows are `user_id`, `display_name`, `is_admin`, `has_availability`—**no emails**. `PeoplePanel` fetches on mount; confirmation must use a separate authorized snapshot, not response rows or fabricated addresses. `wwm_participant_counts` is an owner-list count RPC, not permission to query `auth.users` generally. SQL draft `20260929000000_wwm.sql` restricts `wwm_members` read to self and records `wwm_responses`; roster RPC is intentionally narrow. Hosted deployment/schema state must be verified separately.
- Current `/api/craft/auth/google` requests basic Google OAuth through Supabase with no Calendar scope; `/api/craft/auth/callback` exchanges a code for a session; browser callback completes a create/invite intent. Extend with a **separate, room-bound organizer Calendar consent intent**; never reuse create/invite completion or auto-send on callback. Clarify whether Supabase provider token lifetime/refresh and consent grant can safely support server-only Calendar operations, or use a dedicated backend OAuth flow. Existing public-key SSR client and cookies are not an approved server credential vault. Do not access Hermes personal Google credentials.
- App Supabase access remains through Next APIs and user-scoped RLS. Existing room GET and SSE availability events do not carry confirmation state; add dedicated private confirmation read and mutation endpoints and an explicit refresh/invalidation path, not guessed SSE propagation. Existing `request` helper supports GET/POST but POST is generic; design mutation-specific schema validation and same-origin/CSRF protection. Room time model is local date and half-hour time bounds, with `24:00` in UI but PostgreSQL `time` cannot represent 24:00; confirm actual normalized persistence and date/DST conversion before using it for event boundaries.
- Storybook `src/stories/wwm/wwm.stories.tsx` has RoomAvailability/Everyone/People, mobile/dark, and mock fetches; add isolated consent/review/confirmed/failure stories without real network calls. Existing shadcn Tabs, Dialog, Button, Popover/Calendar and Craft tokens should be composed, not recreated; 4px bounded corners, warm palette, English app copy, visible keyboard focus, no vertical displacement animation, reduced-motion support.

## UI contract (design lane)

**Room identity remains first:** heading/title with concise period and timezone; Share and Settings remain. Confirm tab is a purposeful workflow, not a second dense participant calendar. For members, display confirmed meeting details if present; before confirmation show a calm read-only pending state without owner controls. For owner, first show a compact meeting summary, aggregate availability by date/half-hour with numerator and **membership-based denominator**, distinguish `not responded` from `responded unavailable`, and show an editable proposed interval. No implicit selection of a consequential time.

**Selection:** day columns and 00:00–24:00 half-hour axis, room-range bound, readable count/legend. Mouse drag remains within one date; keyboard-operable start/end selectors and explicit time options offer equivalent path. Touch movement scrolls rather than selecting; stationary taps may stage a range. Do not infer duration across dates or DST gaps/folds from cell count. Announce selected date/time and count accessibly. If proposal changes, keep it local until owner presses **Review confirmation**. An empty/invalid range leaves review disabled and shows inline guidance; no Google or database writes.

**Review dialog:** title, `yyyy.mm.dd`, one-line start–end with IANA timezone and offset where needed, organizer Google account, exact attendee names and addresses, membership total, missing-response/unavailable warnings, and any excluded/missing addresses explicitly itemized. Cancel preserves proposal and returns focus; primary `Confirm & send invitations` is enabled only after recipient policy and credential checks. Do not show sensitive token or invite-link values. If account consent is needed, present **Connect Google Calendar** separately and explain organizer account; return restores proposal/review intent but requires a fresh explicit send press. Decline/cancel/wrong account leaves proposal intact with recovery action, never a send.

**Pending/success/error:** submit disables duplicate clicks, shows stable in-dialog progress. On retriable failure preserve inputs and show scoped error plus retry; on ambiguous timeout show **Checking event status** rather than offering immediate blind resend. On confirmed read-back show immutable date/timezone/attendees and verified Google event link with wording **Invitations requested** (not delivered); owner update/cancel are unavailable until separately designed and approved, and members cannot mutate. Conflict if another confirmation exists should refresh verified state, not overwrite. Dialog and tab remain usable at 375/390/768/1024/1440px and short-height mobile; keep primary action visible, list scroll bounded, no document horizontal overflow, one focus trap. Light/dark and reduced motion must match existing Craft surface styling.

## Backend contract proposed for approval, not implemented

- `GET /api/craft/when-we-meet/[roomId]/confirmation`: authenticated member, RLS-authorized room; returns public confirmation `{status, revision, title, start, end, timezone, organizerDisplayName, attendeeDisplayNames, googleEventUrl?}` and no email except where the organizer is authorized to inspect invite list. `GET .../confirmation/review`: **owner only**, authoritative member/address snapshot, availability counts, consent/account status, confirmation revision. Never expose provider access/refresh tokens.
- `POST .../calendar/connect`: owner-only initiation, room-bound signed state and PKCE/CSRF, narrowly scoped Calendar grant. Callback verifies state, room ownership and expected Google account, stores encrypted tokens in an approved server-side credential store and redirects to room without sending. Explicitly distinguish Google identity linked to Supabase user from organizer Calendar identity; define binding/revocation and refresh failure UX. Exact redirect origins and scope must be approved before console edits.
- `POST .../confirmation`: owner-only, same-origin plus CSRF/state validation, strict room UUID and payload (`start/end` as unambiguous UTC instants plus room-local representations, proposed revision, recipient snapshot/version, idempotency key); server re-reads owner, members/emails, room bounds and slot validity; rejects mismatched/absent recipients and stale preview with a refreshed review response. Server serializes confirmation with unique room/revision reservation and durable state `pending | reconciling | confirmed | failed`, stable deterministic Google event ID and payload hash. `events.insert` with attendees and `sendUpdates=all` only after explicit send; `events.get` verifies ID, time, timezone and attendees. On ambiguous timeout reconcile by deterministic ID before retry, never blindly create another event. Define recovery for crash after Google success but before DB commit, partial API failures, and concurrent submit across devices. Return event link only after read-back; avoid promising email delivery.
- A narrowly scoped owner-only attendee-address resolver is required; `wwm_room_people` cannot provide emails. Approve exact email source, consent/privacy notice, visibility, missing-email behavior, user-account email changes and membership freeze semantics. No general `auth.users` grants or service-role shortcut. Confirmation/outbox tables prefixed `wwm_*` with RLS and narrowly scoped functions; credential ciphertext/keys live outside exposed room records, with retention/revocation defined. Schema and hosted SQL require independent approval.
